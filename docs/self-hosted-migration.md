# 自建服务器改造决策与实施记录

## 已确认的方向

- 服务器：Ubuntu 22.04 64位、华东1（杭州）、2 vCPU / 2 GiB；域名正在 ICP 备案。
- 技术方案：Node.js 24 / CommonJS、Fastify、PostgreSQL 17、WebSocket（服务端 `ws`）、Nginx、Docker Compose。先做单应用和单数据库，不预先增加Redis、微服务或Kubernetes。
- 旧用户、战绩和文件无需搬迁；新系统从全新数据库开始。无需搬迁不代表授权删除旧云端数据或停用服务。
- 用户同意实施，并要求优化原先受云开发限制的功能，不必照搬旧实现。保留功能完整性、可信身份、积分安全整数和事务一致性；涉及玩法、人数或数据留存的变化要列明，不把全部旧代码当成不可调整规则。
- 迁移在 `codex/self-hosted-migration` 进行；`codex/cloudbase-baseline` / `77c54eba3b1bfbd8f446f950263af202717bd1b5` 长期保留，不在其上开发或删除。

## 当前代码交付范围

`server/` 已形成完整的单机自建后端代码：配置和迁移校验、微信登录与哈希会话、资料和头像、房间生命周期、事务计分与流水、结算/解散、战绩、微信小程序码、同端口WSS、限流、日志脱敏和健康检查。数据库迁移为 `001_identity.sql`～`004_history_qrcode.sql`，当前接口见 [server/README.md](../server/README.md)。

`miniprogram/` 已通过 `utils/backend.js` 接入上述REST/WSS，已无 `wx.cloud` 调用。登录、资料、头像、创建/加入/退出、房主转移、全部计分动作、流水、结算/解散、战绩、二维码、永久UUID邀请和新版scene均已有客户端映射；6位房间号只用于展示和手工加入。

关键实现边界：

- 身份只来自Bearer会话；请求中的用户ID、昵称和头像不作为可信数据。
- 房间、调用者、成员按统一顺序加锁；积分、奖池、stateVersion、流水和幂等回执同事务提交。明确回滚的竞争有界重试，COMMIT结果未知由客户端复用原operationId重试。
- 允许负分、允许任意未退出成员领奖池；底注和All-in使用事务内最新值。所有参与者积分加奖池必须为0，运算经过BigInt和安全整数边界检查。
- 最后退出或房主解散删除本局及流水、不生成战绩；结算要求空奖池并保存不可变最终快照。操作回执不随房间删除，避免旧请求复活业务。
- 头像经真实内容校验、限像素和重编码后保存到独立目录；替换成功后仅逐个清理旧文件。二维码以每房最多256 KiB的PNG存数据库，网络和解码不占用房间事务。
- WSS只发送可信快照和终止/撤权事件，不执行写命令；客户端只接受更高stateVersion，断线后以有上限的低频REST重新校正。

## 当前验证与部署边界

本地测试分三层：根 `npm test` 验证小程序和旧云端兼容行为；`npm --prefix server test` 使用PGlite和HTTP替身验证新后端；`npm --prefix server run test:postgres` 提供显式隔离的真实PostgreSQL多连接入口。PGlite会执行真实SQL，但单连接排队不能证明PostgreSQL 17行锁竞争、网络、容量或受限角色在完整版本上的真实表现；微信替身也不代表真实平台联调通过。

当前完整代码尚未部署。`miniprogram/config.js` 的生产HTTPS地址为空；现有Ubuntu隔离环境仍是提交 `0f0a086` 的基础后端镜像，只验证过ready、受限数据库账号、回环API端口和空闲资源，不包含002～004、头像卷、业务接口、WSS或新版小程序。旧线上小程序继续使用微信云开发，旧服务和数据未停用或删除。

正式切换前仍需完成：完整迁移及授权、镜像重建、HTTPS/WSS和微信合法域名、真实微信登录/二维码/扫码、真机、多账号弱网、真实PostgreSQL多连接竞争、外网端口隔离、重启、数据库与头像一致备份恢复、留存/删除流程、容量告警和上线窗口。宿主机已有80端口Nginx，合并配置前必须核对用途，不能直接覆盖。

## 云开发限制与优化清单

以下为逐步改造目标；资料/头像、房间生命周期、计分、结算/战绩、二维码、前端REST适配及单实例WSS代码已按上文落地。生产配置、部署、真实微信/真机、多账号弱网和真实PostgreSQL多连接验收仍待完成。

| 现有实现及证据 | 自建后端改造方向 | 防止误改 / 验收要求 |
| --- | --- | --- |
| 房间整包 `players` 数组更新；见三个云函数 | 玩家和房间按关系模型存储，用统一锁顺序及事务更新，减少覆盖 | 计分、加入、退出、结算竞争时账本正确；一个用户只关联一个活跃房间 |
| 最近50个 `recentOperationIds`；见 gameLogic | 持久化操作记录，绑定房间、用户、操作ID并校验参数摘要；保留窗口与房间生命周期明确约定 | 超过50次后的网络重放也不重复记分；相同ID不同参数拒绝 |
| 最近100条消息嵌入房间；见 messageUtils 和 room 页 | 流水独立存储、游标分页；实时只传必要更新或通知，断线获取完整校正 | 不把“只展示最新一页”误当成“只能保留100条”；保留期和存储预算另行明确 |
| 云数据库 watch 及失败轮询；见 room 页 | 自建WSS房间订阅、心跳、抖动退避重连、版本校正与低频回退 | 不继承平台连接配额，但容量仍须压测；推送失败不能丢账或重复计分 |
| 云存储 fileID / 临时URL；见 home、roomFunctions | 平台无关永久资源ID、受管上传目录、鉴权/限时访问、独立存储适配层 | 防越权读写和任意路径；上传存储不随应用镜像更新而丢失 |
| 6位房间号无显式碰撞重试；见 roomFunctions/create | 数据库唯一约束与有上限的碰撞重试；内部房间ID与展示房间号解耦 | 不能覆盖旧房间；过期邀请不得因房间号复用误入新局 |
| 每局8人、批量最多7人；同时涉及数组体积和UI | 在房间模块阶段重新评估可配置人数与前端布局，不把8当作服务器固有限制 | 不是立即放开无限人数；需确认界面、操作规则及并发成本 |
| 结算后清理活跃信息；见 roomFunctions/settle | 重新评估可追溯流水与历史详情、分离业务保留期与技术删除时机 | 完整流水是否对用户开放及保存多久需明确；不默认永久保存所有隐私数据 |
| 旧 `allInVal`、旧消息文档兼容分支 | 全新后端不搬入无数据迁移需求的历史兼容层 | 现有玩法和必要入口保留；旧版客户端/分享入口另做版本与停写处理 |

积分守恒、服务端鉴权、并发事务、金额校验以及幂等属于正确性要求，不是云开发限制。普通转分、下注、底注、All-in、领奖池、结算、战绩和分享仍需在新系统完整支持。无需为保留原版再让新后端使用云数据库。

## 剩余验收与切换顺序

1. 在独立环境把数据库迁移到004，执行当前受限账号授权，重建带头像卷和WSS的API镜像；逐项复核ready、权限、持久化和回环端口。
2. 用专用PostgreSQL 17测试库运行多连接竞争脚本，并完成重启、数据库与头像一致备份及恢复演练；按真实负载评估2 GiB容量。
3. 配置域名、HTTPS/WSS和微信合法域名，在真机完成真实登录、头像、二维码、分享扫码、多账号并发、断网重试和前后台恢复。
4. 确认操作回执、结算房间、战绩、审计流水、头像和过期会话的留存/删除规则、容量告警与人工清理流程。
5. 制定维护窗口切换：先处理旧端活跃房间和停写，避免新旧后端形成双账本；只有用户明确确认后才正式发布和停用旧服务。

新系统已有写入后不能简单切回旧数据库；要先停写并制定新增数据处置方式。旧版代码始终保留，旧云服务是否停用另行确认。
